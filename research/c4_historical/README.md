# Phase 6.5B — versioned Weekly J and C4 research history

This directory is **research only**. `RESEARCH_HISTORICAL` is a reconstructed series, not a record of signals actually published on those dates. It is not imported by production, the homepage, ranking, live, Forward, or the official append-only history. No `FINALIZED_CLOSE` row is rewritten.

## Weekly J governance

`weekly_j_versions.js` explicitly implements the existing `buy-point-core.js:weeklyKdj` weekly OHLC aggregation and K/D/J arithmetic: seed `K=D=50`, nine-week rolling high/low, `RSV=50` when high equals low, `K=2/3*K+1/3*RSV`, `D=2/3*D+1/3*K`, `J=3*K-2*D`, with no intermediate rounding. The versions differ **only** in the week key. Both use UTC calendar arithmetic, not host-local `getDay()`/`setDate()` or `process.env.TZ`.

- `WEEKLY_J_PRODUCTION_LEGACY_V1` is the historical compatibility version. It explicitly replays the official GitHub Actions UTC-process behavior: parse each Taiwan trading date at Taipei midnight (`UTC−8h`), take that instant's UTC weekday, and anchor it to the preceding UTC Monday. A Taipei Monday is consequently attached to the previous week's key; Tuesday begins the next key. This is not a claim that the grouping represents a correct Taiwan trading week. Current production still uses the original helper; this research helper is parity-verified against its stored FINALIZED outputs.
- `WEEKLY_J_TW_TRADING_WEEK_V2` anchors the Taiwan calendar date to its Monday. Monday–Friday trading observations form the same week and shortened holiday weeks are valid. Historical exchange make-up Saturday rows, when present in the source, remain assigned to the preceding Monday rather than being silently dropped; this preserves identical OHLC input coverage for the comparison. V2 is research-only, not active production. A target-date calculation slices input through that date, so an incomplete current week never sees future Thursday/Friday data.

The primary research dataset uses **Legacy V1** exclusively. `weekly_j_comparison.json` summarizes Legacy versus V2 on the same as-of adjusted OHLC: different J days, mean/max absolute J difference, and different displayed C4 and decision-level days. It contains no V2 production scores or UI feed.

Known current-source cases (Legacy / V2 J): 0050 2026-09-18 = `100.99812531854704 / 101.88526432173711`; 00662 2026-09-17 = `46.935222189938884 / 49.96017164534835`; 00830 2026-09-18 = `40.427473449632515 / 39.436665395947`. Tests run the same source in UTC, Asia/Taipei, and America/New_York.

## Generation, provenance, and immutability

Run manually: `node scripts/build_c4_research_history.js --fetch --end YYYY-MM-DD`. The builder fetches FinMind `TaiwanStockPrice`, `TaiwanStockDividendResult`, and `TaiwanStockSplitPrice`, then for each date truncates price and corporate actions to that date. It uses official `adjustPriceHistory`, requires 252 native adjusted OHLC observations, computes DD52/Crash with the unchanged production helpers, and invokes `HSFinalCoreProduction.buildFinal` with the Legacy weekly J. The first valid date requires all three factors. 009815 remains zero records until its own history matures; there is no proxy.

Output is `source/{symbol}.json`, `{symbol}.json`, and a single comparison summary. The source file preserves the fetched response, including retrieval time. Each primary artifact records the source hash, records hash, artifact hash, formula/strategy ID, Weekly J version, generation-time HEAD, **builder and weekly-helper content hashes**, generated time, and sample range/count. `generation_commit` identifies the HEAD present when the manual build ran; it need not contain the subsequently committed artifact itself. The code-content hashes identify the actual research implementation used. Numerical records regenerate deterministically from the same source under any runtime timezone. Existing files require explicit research-only `--regenerate` to change.

Before any output is written, the builder compares every overlapping `FINALIZED_CLOSE` row for Weekly J, DD52, Crash raw/score/contribution, raw total, display score, and level. Float differences are limited to `1e-10`; score, display score, and labels must match exactly. `level` uses the existing `HSDecisionLayerV1.STAGES` applied to the displayed official score; the separate official `tier` is also checked against `HSFinalCoreProduction.labelFor(exact)`. Any mismatch, or zero overlap for a nonempty symbol, stops publication. The 2026-09-18 source produced 18 matching overlap rows each for 0050/00662/00830/00935 (72 total); 009815 had no mature record.

The original point-in-time provider response and adjusted OHLC bundle behind each old FINALIZED row were **not** retained, so current FinMind-source parity cannot prove historical raw responses were byte-identical. It does prove this reconstruction reproduces the stored official factor/score fields on all current overlaps. Phase 6 UI/Phase 7 may consume the primary research series for distributions/outcomes only after separate scope approval; latest official state and eligibility must continue to read FINALIZED.
